# 论文阅读或报告的要点

对于论文阅读是理解论文，从论文中**获取信息量**，需要关注应该从论文了解哪些的信息。报告是在获取信息知识后，**整理输出**的蒸馏过程，需要进一步的总结归纳信息，并按照一定的逻辑表达输出。通常我按以下思路学习拆解论文：

- 首先，忠实原文阅读理解论文或讲解报告论文，按照原文表达的观点要点、内容章节进行介绍。总结归纳论文，分析论文在什么场景下，做了什么事情，其中采用了什么样的具体方法，得到什么样的效果。
- 其次，总结其中可以可以学习借鉴的地方，包括研究内容选题、研究思路、技术手段、写作表达方式等不同角度。
- 最后，分析论文中的优劣，发挥自己的主观评价意见，哪些地方做的不足，哪些地方做的有亮点，扩展更多的研究思路或者想法。

另外报告ppt应多关注逻辑性和视觉要素，包括：

- 构建目录，汇总简化内容，增强表达逻辑性
- 多做**流程图、效果图、数据表格**，图的信息量比文字更吸睛；
- 在系统图上，适当虚线框可以更好的强调想要表达论文主要工作。
- 多使用用短语。大段长文本增加阅读障碍感；
- 对关键信息，多**放大加粗，以强调重点**；
- **前后呼应**，前面提出问题，后面技术手段一一对应问题

# Web应用访问控制漏洞的自动化黑盒检测
《BACScan: Web应用程序访问控制失败漏洞的自动黑盒检测》（BACScan: Automatic Black-Box Detection of Broken-Access-Control Vulnerabilities in Web Applications）发表于 ACM CCS 2025（ACM计算机与通信安全会议，网络安全领域公认的顶级学术会议）。

## 背景故事与问题

现有黑盒扫描器在检测访问控制漏洞（BAC）时一般采取响应相似性判断（response-based oracle），即用攻击者身份重放受害者的请求，若返回内容相似，则判定存在漏洞。读取型越权（RBAC） 有效，因为泄露的数据会直接出现在响应里。但对于修改型越权（MBAC） （如越权删除订单、修改他人病历），直接响应通常不包含修改是否成功的证据。

## 核心方法

这篇论文的核心方法是基于反馈驱动的检测框架。在上述场景下，这篇论文摒弃传统判据，转而利用页面间的数据依赖关系。一个页面修改的数据，通常会在另一个状态页（status page） 上展示出来。例如，在添加订单页面提交的数据，会出现在订单列表页面上。因此，可以通过受害者的会话去检查状态页上数据的变化，确认攻击者的越权修改是否真正生效。这里存在2个问题，一是如何自动找到与修改页对应的状态页；如何保证攻击者重放请求时，应用处于可被修改的正确状态。

> 其实从场景需求的原始想法上，这是非常简单的一个方法，然而这篇论文却能发顶会。这是因为一方面真实存在的需求驱动打动了审稿人，另一方面在算法、写作、实验等几个方面的包装工作都做得非常好。

## 创新点

- 提出反馈驱动的MBAC检测新范式。揭示了传统“直接响应相似度”判据在MBAC场景下的根本性失效，并首次系统性地提出利用跨页面数据依赖的反馈来判定越权修改是否成功。

- 设计IDDG与高效构建算法。引入页面间数据依赖图（IDDG） 这一数据结构，并设计了结合令牌插入与层次化遍历的自动化构建方法，解决了黑盒条件下“状态页发现”的难题。

- 设计针对修改类型的重放策略。特别是针对DELETE类型漏洞的“先插入后删除”重放机制，确保了检测的可靠性。

- 实证效果显著。在20个真实应用中发现89个漏洞，其中54个为0-day，35个获得CVE编号。与SOTA工具EvoCrawl和BurpSuite相比，BACScan在MBAC检测上的精确率和召回率均有大幅领先（MBAC精确率100%，召回率92.98%）。

## 写作学习


### 论文标题调整？

这篇论文的BACScan: Automatic Black-Box Detection of Broken-Access-Control Vulnerabilities in Web Applications 标题直译为中文是 《BACScan：Web 应用中访问控制失效漏洞的自动化黑盒检测》，存在研究内容泛化的问题。Broken-Access-Control 直译是访问控制（策略）失效，[OWASP 官方](https://bbs.huaweicloud.com/blogs/400993#1)将访问控制失效定义为访问控制策略没有被正确执行，导致用户能够执行超出其预期权限的操作。越权是其典型的表现，实际上**访问控制失效包括越权和其他更多情况**。比如，制定了错误的访问控制策略、CORS配置错误、访问控制策略缺失等情况。对于这篇文章的内容，实际只研究其中能够表现为未授权读取和数据修改的两类越权操作漏洞，如果精准表达研究内容，中文含义应该对应 《BACScan：Web 应用程序访问控制越权漏洞的自动化黑盒检测》（BACScan: Automatic Black-Box Detection of Access Control Bypass Vulnerabilities in Web Applications）或者《BACScan：Web 应用程序中读取型与修改型访问控制漏洞的自动化黑盒检测》 （BACScan: Automatic Black-Box Detection of Read- and Modification-Based Access Control Vulnerabilities in Web Applications）。

论文命名的用词没有那么绝对的答案，在泛化的专业术语和准确的描述之间，ChatGPT对使用泛化统一的术语的的考虑如下：
- **保持学术分类的一致性**。Broken Access Control是一个已经形成的安全漏洞类别。使用这个术语，能够让读者迅速知道论文属于 Web 访问控制安全研究领域。
- **避免将技术实现等同于研究问题**。论文采用什么技术检测漏洞，与论文研究的漏洞类别并不是一回事。
- **保持研究问题的抽象层次**。学术论文标题通常描述研究对象，而不是穷举所有具体场景。例如，研究 SQL 注入检测的论文，不需要将标题写成针对 GET、POST、Cookie 参数的注入检测
- **保留研究成果的领域定位**。使用 Broken Access Control，能够让研究成果与访问控制漏洞检测领域建立直接联系，而不是将其归入宽泛的未授权数据操作检测。

专业术语解决的是**这篇论文属于什么研究领域**，精确限定解决的是**这篇论文实际研究了什么问题**，对于存在明显研究边界的论文，应该采用**专业术语、研究范围限定**的严谨表达方式。

### 摘要写作

论文摘要翻译如下：

```
访问控制中断(BAC)漏洞一直被列为web应用程序中最关键的安全风险之一，在过去几年里一直占据OWASP top 10的榜首位置。这些漏洞允许攻击者绕过访问控制机制并执行未经授权的操作，对敏感的业务和用户数据构成安全和隐私威胁。尽管对BAC漏洞给予了大量关注，但检测这些问题的有效和可靠方法仍然有限。

在这项工作中，我们提出了BACScan，一种新的黑盒方法来检测web应用程序中的BAC漏洞。与现有的基于响应相似性的oracle只检查未授权的读访问不同，BACScan引入了一种创新的反馈驱动的oracle，它通过推断操作依赖的网页和分析操作反馈来确定是否发生了未授权的读或修改操作。我们在20个实际应用程序中评估了BACScan，并成功识别了89个漏洞，其中包括54个以前未报告的漏洞，性能优于最先进的工具。我们向受影响的供应商报告了所有新发现的漏洞。到目前为止，已经分配了35个新的CVE id。
```

论文摘要分为2部分，第一部分1~3句话均是描述失效的访问控制漏洞；第二部分，第4句话提出新方法；第5句话对比新方法和旧方法的区别；第6~8句话描述新方法的效果，以及效果的反馈验证。

# 基于动态贝叶斯估计的实用互联网规模拓扑监测

这篇是计算机网络与网络系统领域顶会NSDI 2026年的论文BayWatch: Practical Internet-Scale Topology Monitoring with Dynamic Bayesian Estimation。

## 论文工作简介

这篇研究的是互联网规模的多路径拓扑监测。现有互联网拓扑测量/监测方法有两个关键局限：
- 拓扑不完整。现有多路径发现算法（如 MDA、D-Miner）假设负载均衡路由器（LB 路由器）在后继节点之间均匀分流，即各后继收到探测包的概率相同。但真实互联网中负载均衡响应分布（LBR distribution）往往不均匀，导致大量节点和链路被漏掉。
- 探测效率低、缺乏时间感知。现有方法每个快照都“从头重新发现拓扑”，大量探测浪费在反复验证稳定链路上；同时孤立快照难以区分正常拓扑演化和异常事件。

作者设计了一个基于动态贝叶斯网络（DBN） 的互联网规模拓扑监测系统。它估计真实 LBR 分布并预测其时间演化，从而在提高拓扑完整性的同时显著减少探测开销，并支持异常检测。

## 核心工作

### 测量并挑战 均匀负载均衡LBR 假设

- 作者随机选取 10,000 个 IPv4 /24 前缀，发送大量随机流标识探测包，近似测量各分歧节点后继的响应频率，即 LBR 分布。
- 用 **Gini 系数（GC）** 量化分布均匀性。结果发现：只有约 20% 的情况接近均匀；约 23% 的分布 GC > 0.3，约 10.6% 的 GC > 0.5。
- 在 Topology Zoo 的 100 个受控拓扑上测试 D-Miner：当 GC = 0.4 时，D-Miner 漏掉 **24% 节点、60% 边**。
- 解释非均匀来源：WCMP 配置、MPLS 隧道、ICMP 不响应节点等。

### 用 动态贝叶斯网络DBN 建模包转发与拓扑演化

BayWatch 的核心建模思路：

- IP 逐跳转发具有**一阶空间马尔可夫性**：下一跳只依赖当前路由器状态。
- 拓扑动态演化具有**一阶时间马尔可夫性**：当前时刻状态只依赖上一时刻。
- 二者结合构成 **Dynamic Bayesian Network（DBN）**：
  - 节点表示路由器接口；
  - 边表示条件转发概率；
  - 相邻时间片之间连接对应节点，表达时间依赖。
- 作者用似然比检验验证一阶马尔可夫假设，得到的 p 值分别为 0.95 和 0.68，支持该建模。

### 估计 LBR 分布

- 将同一 TTL 的节点组织成一层，相邻层节点全连接，把 LBR 分布表示为**层间转移概率矩阵**。
- 估计三组参数：第一层初始分布、相邻层转移概率、最后一层到观测值的观测概率。
- 由于隐变量后验难以精确计算，采用**变分推断**，最大化 **ELBO**，通过 E/M 式迭代更新参数。

### 预测 LBR 分布的时间演化

- 将每个快照表示为转移矩阵组成的张量。
- 为解决不同快照节点集合不一致的问题，采用**节点对齐策略**：每层保留过去 g 个快照中出现最频繁的 k 个节点，并增加一个 “others” 节点聚合稀有/新节点。
- 对第 g+1 个快照引入变分分布，最大化 ELBO，得到预测的 LBR 分布，用于指导探测和异常检测。

### 两种运行模式与轮次探测

- **Bootstrap 模式**：无历史数据时，每个 /24 前缀每跳先发 6 个随机流标识探测包，作为初始拓扑和参数估计起点。
- **Predictive 模式**：有历史数据时，先预测当前 LBR 分布，复用历史流标识验证稳定边；若发现历史中从未出现的新边，则该跳回退到 bootstrap 模式。
- 每轮根据估计的转移概率计算每跳所需最少探测数，并利用前几轮已发送探测数进行扣减，避免重复探测。
- 通过多层贝叶斯网络逐轮更新，直到各跳所需探测数降为零。

### 异常检测

- 持续监测中，比较预测 LBR 分布与实际测量。若某些节点持续偏离预测，则标记异常。
- 案例：2025 年 8 月 15 日检测到 Zayo 网络内部 rehashing 节点数量激增，与外部报告的 Zayo/ServiceNow 服务中断时间吻合。


## 写作学习

### 摘要

这篇论文摘要分为2部分。第一部分，第1句强调网络拓扑重要性，然后第2句列举2个现有方法不足。第二部分，第1句提出新方法，第2句解释原理，第3句表达实验结果，第4句是真实场景验证。摘要原文如下：


# 连接器生态的账户认证安全问题

《揭秘连接器生态系统中基于oauth的帐户链接的安全》（Demystifying the (In)Security of OAuth-based Account Linking in Connector Ecosystems）这篇文章来自四大安全顶会S&P 2026。

## 背景知识

这里先介绍OAuth 2.0、OIDC（OpenID connect，开放身份连接）、SSO（Single Sign-On，单点登录）

- OAuth 2.0。OAuth 2.0 是授权协议。用户（资源所有者）授权一个第三方应用（Client），让这个应用代表用户去访问某个受保护资源（Resource Server）。授权服务器（Authorization Server）发放 Access Token，比如Google、微软、微信、支付宝这类的大厂，在用户授权后，应用可以拿着第三方应用拿着 Access Token 去访问对应资源服务器上的 API。
- OIDC。OIDC是建立在 OAuth 2.0 之上的身份认证层，可以让应用能够安全地验证当前登录的用户是谁。授权服务器发放Access token和ID Token，应用可以通过ID Token确认用户身份，同时OIDC标准化了 userinfo、discovery、JWKS 等身份相关端点和 ID Token 的验证规则。前者通过用户授权应用可以做什么，后者可以识别用户身份。
- SSO。SSO有多种实现，一般常用的云服务应用、移动App等使用OIDC，对于企业客户或者传统ldP使用SAML 2.0，CAS常见于校内网Web应用认证，Kerberos在企业内部域环境下使用。

## 论文简介

这篇论文讨论账户关联的安全问题。论文定义连接器生态（Connector Ecosystems），用户通过OAuth 2.0获得用户对外部服务的授权，这类外部服务成为连接器；其中，用户的Access Token和应用方的用户身份之间的绑定是账号关联（Account Linking）。论文指出 OAuth 标准只规定了应用如何从用户处拿到 token（first-order OAuth），却没有规定 token 应关联到应用中的哪个用户（second-order OAuth）。当应用与其 OAuth client 跨源、跨 User-Agent、甚至跨租户部署时，就会出现授权上下文缺失，导致严重的账号错绑（account mislinking）和账号接管。

论文的提出并命名了两种攻击方式：

- Cross-user OAuth Session Fixation（COSF）。攻击者可预先固定（fixate）一个受控的 OAuth session，诱骗受害者完成授权，结果受害者的 connector 授权被绑定到攻击者的应用账号上。 OAuth session可能是带有攻击者的应用账号和被攻击者的授权请求。

- Cross-tenant 攻击。在 OAuth-as-a-Service（OaaS）多租户架构中，恶意租户可利用共享 client_id 或共享 redirect_uri 发起 Cross-tenant Client ID Confusion 和 Cross-tenant COAT，接管其他租户中用户的 connector 授权。

作者还开发了 OASIS（OAuth Session Integrity Scanner）静态分析工具，用于在 Android 应用中识别账号关联实现并检测 COSF 漏洞；并在 46 个厂商上做了测量，发现 42 个厂商存在账号错绑风险，其中 40 个受 COSF 影响，8 个 OaaS 提供者存在跨租户问题。作者进行了负责任披露，获得 20 个厂商确认、15+ 修复、35,850 美元赏金，并推动 IETF OAuth 安全最佳实践更新。

> 这篇论文核心贡献是发现广泛使用协议的缺陷，构建系统，像使用该协议的厂商披露修复漏洞，并推动完善协议。

## 论文怎么做的

### 梳理连接器生态与 OAuth 账号关联架构

论文将连接器生态分为三类：

- **Connector-equipped Apps**：如 Evernote、Notion，内置少量特定 connector。
- **Integration Platforms**：如 IFTTT、Microsoft Power Automate、Amazon Alexa、Google Home。
- **Agentic AI Infrastructures**：如 Amazon Bedrock AgentCore、Microsoft Copilot Studio、Composio，采用 **OAuth-as-a-Service（OaaS）**，由集中式 **Token Vault** 统一管理 OAuth token。

论文指出，OAuth 标准只处理“应用作为一个逻辑实体获取 token”，但账号关联需要进一步回答：**这个 token 应该绑定到应用中的哪个用户？** 论文将 OAuth connection 的授权上下文形式化为三元组：

> **OAuth connection = <user, tenant, connector>**

其中 user 是应用用户身份，tenant 是 OaaS 中的租户，connector 是外部服务。

### 分析解耦式 OAuth 架构带来的三个挑战

- **Cross-Origin Session Tracking**：账号关联跨多个 Web origin，回调 origin 因同源策略无法读取发起 origin 的用户 session。
- **Cross-UA Session Tracking**：原生 App 按 RFC8252 用外部浏览器完成 OAuth，但浏览器与 App 进程隔离，无法共享用户 session。
- **OaaS 中 OAuth 职责外包**：Agent 把 OAuth 职责交给 Token Vault，而 Agent 自身用户 session 在租户自己的 Web/原生/IM 渠道中，形成多重 session gap。

### 归纳常见但有缺陷的实现模式

作者发现两类常见设计：

- **OAuth session 放在独立 URL 参数中**：在 OAuth initiation 与 authorization 之间插入 pre-authorization 请求，用 `sessionID` 等 URL 参数跨 origin/UA 传递 OAuth session。
- **OAuth session 嵌入 state 参数**：直接把 OAuth session 标识放进 `state`。

这两类设计都允许 OAuth session 被固定、暴露给任意 origin，并传播到 OAuth callback，从而破坏 session integrity。

### 提出 COSF 攻击与跨用户攻击

**COSF 攻击流程**：

1. 攻击者用自己的应用账号发起账号关联，记录 pre-authorization URL（含 OAuth sessionID）或 authorization URL（state 中编码 OAuth session）。
2. 攻击者把该链接发给受害者。
3. 受害者点击后，浏览器被重定向到授权端点。
4. 若已有 prior consent，授权自动完成，code 和 state 回到应用 OAuth callback。
5. 应用 OAuth client 用受害者的 auth code 换 token，并按被固定的 OAuth session 把 token 关联到**攻击者的应用账号**。
6. 攻击者获得受害者 connector 的未授权访问。

论文还讨论了两个相关实现缺陷：

- **App Account Login CSRF**：OAuth session cookie 同时承载应用完整用户 session，导致应用账号登录 CSRF。
- **0-Click Forced Linking**：OAuth session ID 可猜测（如 8 位用户 ID 或无签名 JSON），攻击者可伪造 OAuth session 并提交自己的 auth code，强制受害者访问攻击者的 connector 账号。

### 提出跨租户攻击（OaaS 场景）

- **Cross-tenant Client ID Confusion**：多个租户共享同一个内置 client_id，用户在良性租户下对某 connector 的授权 consent 会被恶意租户“继承”，导致静默授权给恶意 agent。
- **Cross-tenant COAT**：OaaS 中 Token Vault 使用跨租户、跨 connector 共享的 redirect_uri，恶意租户可借助自己的恶意 connector 把受害者的 auth code 转发到恶意 connector，再在良性 connector 处兑换，实现账号接管。

### 提出防御措施

论文给出三类稳健防御（D1–D3）：

- **D1 Web App Cross-Origin Defense**：OAuth callback 注册在用户 session 所在同一 origin，回调时校验 OAuth session 与用户 session 绑定。
- **D2 Native App Cross-UA Defense**：原生 App 注册 native public client callback，收到授权响应后把 auth code 交给后端 confidential client，并校验 OAuth session 与用户 session。
- **D3 Post-redirect Pattern**：回调端点作为代理，把 auth code 和 state 转发回原 authenticated origin/UA，再校验绑定。

还讨论了 D4–D6 等补充防御：手动 PIN 桥接、OAuth client 额外 consent 屏、浏览器重新认证，并指出其局限。针对 OaaS，进一步提出 **per-tenant OAuth client registration（BYOC）** 和 **globally unique per-connector redirect_uri**。

### 开发 OASIS 静态分析工具

OASIS 分两阶段：

- **Phase I：账号关联识别**。从 AndroZoo 收集 Productivity 类、近 6 个月更新、至少 50K 下载的 APK；用 Jadx 反编译，解包 JS bundle 和 React Native Hermes 字节码；用启发式规则筛选：connector 图标/名称共现、排除 OAuth public client、排除本地 App intent 交互；聚焦 Dropbox、OneDrive、Outlook Calendar 三个 connector；再辅以人工收集。
- **Phase II：COSF 漏洞检测**。采用排除式思路：若 App 本地代码中同时解析 OAuth callback 的 `code` 和 `state`，且不解析 `id_token`，则判为 Secure；否则判为 Vulnerable。

### 测量与披露

- 收集 46 个厂商，42 个存在账号错绑风险。
- 40 个厂商受 COSF 影响；3 个存在 App Account Login CSRF；4 个存在 Connector Account Forced Linking。
- 8 个 OaaS 提供者中，6 个受 COSF 影响，4 个存在 Cross-tenant Client ID Confusion，7 个存在 Cross-tenant COAT。
- 对 27 个有 Android App 的厂商运行 OASIS Phase II：20 个 true positive、4 个 true negative、3 个 false negative、0 个 false positive。
- 负责任披露：20 个厂商确认，15+ 修复，35,850 美元赏金；Amazon Bedrock AgentCore、Arcade 等采纳了作者根因分析和修复建议；作者在 IETF OAuth Working Group 推动 Internet-Draft，并已被采纳为 OAuth WG Draft。

---

## 创新点

1. **首次系统研究连接器生态中的 OAuth 账号关联安全**。将 OAuth 从传统 client-server 模型扩展到 connector-equipped apps、integration platforms、agentic AI infrastructures，并提出 **OAuth connection = <user, tenant, connector>** 的授权上下文模型。

2. **提出 COSF（Cross-user OAuth Session Fixation）新攻击类**。这是首次针对标准 OAuth 2.0 authorization code grant 中 **session fixation** 的系统性分析；与传统 Web session fixation 不同，COSF 固定的是从用户 session 派生的 OAuth session，用来劫持后续授权。

3. **揭示 OAuth-as-a-Service 多租户信任边界问题**。提出 **Cross-tenant Client ID Confusion** 和 **Cross-tenant COAT** 两类 confused deputy 攻击，扩展了此前 single-tenant COAT 的工作。

4. **提出 OASIS 静态分析框架**。用排除式静态分析在 Android App 中识别账号关联实现并检测 COSF；不执行实际 OAuth 流程即可发现漏洞，兼容 Java/Kotlin、Ionic/Capacitor、React Native 等多种 App 类型。

5. **提出可落地防御并推动标准化**。D1–D3 稳健防御、OaaS 下的 post-redirect 防御、BYOC、globally unique redirect_uri；并推动 IETF OAuth 安全最佳实践更新。


## 四、主要贡献点

论文贡献包括：

1. **梳理 OAuth 架构模式与安全挑战**：揭示 textbook OAuth 和相关工作未覆盖、但对连接器生态至关重要的账号关联架构与安全问题。
2. **提出 COSF 攻击类与综合防御**：系统化描述 Cross-user OAuth Session Fixation，并给出 D1–D6 防御。
3. **扩展到 OaaS 跨租户 confused deputy 威胁**：分析 Cross-tenant Client ID Confusion 与 Cross-tenant COAT。
4. **开发 OASIS**：识别移动 App 中的账号关联支持并检测 COSF 漏洞。
5. **大规模测量**：在 42 个厂商中发现漏洞，覆盖 Slack、Alexa、n8n、IFTTT、Perplexity、Manus、Amazon Bedrock AgentCore、Microsoft Copilot Studio、Composio 等。
6. **负责任披露与标准化影响**：20 个厂商确认、15+ 修复、35,850 美元赏金；推动 IETF OAuth WG Draft。

# 预训练模型解析日志

《利用预训练的语言模型释放基于语义的日志解析的真正潜力》 （Unleashing the True Potential of Semantic-based Log Parsing with Pre-trained Language Models）是2025年CCFA类顶会 ICSE（International Conference on Software Engineering，国际软件工程大会）的论文。

## 论文简介

这篇论文研究日志解析，把原始日志消息解析成日志模板和动态参数的结构化形式进行解析。作者主张通过设计得当的小型预训练语言模型（PLM）也，在日志解析上取得与最先进大模型方法同等或者更好的解析效果，同时更高效、成本更低、隐私更可控。在技术上，作者在日志语义解析的三个阶段（采样、微调、推理）中加入增强方法，增强预训练模型的效果。

## 摘要写作

论文摘要内容原文翻译如下：

```
软件密集型系统经常产生控制台日志，用于故障排除。日志解析旨在将日志消息解析为特定的日志模板，通常作为自动化日志分析的第一步。为了更好地理解日志消息的语义信息，已经提出了许多基于语义的日志解析器。这些日志解析器对一个小型的预训练语言模型(PLM)(如RoBERTa)在一些标记日志样本上进行微调。随着大型语言模型(大型语言模型)的日益普及，最近的一些研究也提出利用大型语言模型(如ChatGPT)通过上下文学习进行自动日志解析，并获得比以前使用小型PLMs的基于语义的日志解析器更好的结果。在本文中，我们展示了使用小型PLMs的基于语义的日志解析器实际上可以实现比最先进的基于llm的日志解析模型更好或相当的性能，同时更高效和更具成本效益。我们提出了一种新的基于语义的日志解析方法UNLEASH，该方法结合了三种增强方法来提高PLMs的日志解析性能，包括:(1)基于熵的排序方法来选择信息量最大的日志样本;(2)一种对比学习方法，以增强微调过程;(3)提高日志解析性能的推理优化方法。我们在一组大规模的公共日志数据集上评估了UNLEASH，实验结果表明，与最先进的日志解析器相比，UNLEASH是有效和高效的。
```
{: .wrap}

这里总结摘要模板的写作思路如下：
- 第1~3句是业务场景和需求；
- 第4~5句引入PLM和LLM，业界通常认为后者比前者效果好；
- 第6句**提出相反的主张**，新方法可以做到PLM比LLM效果好，并介绍新方法的在技术方面的3个优化；
- 第7句在最后说明实验效果。
