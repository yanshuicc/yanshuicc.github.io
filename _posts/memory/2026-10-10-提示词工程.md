# 大模型中文AI味

## 一、AI味的原因

大模型在选词和造句时，会偏向语料里高频、安全、万能的表达。结果就是句子像报告、像摘要、像PPT，不像人在说话。

1. **训练语料模板化**：模型学的是百科、教程、公文、公众号、论文摘要、营销文案，这些本身套话多。  
2. **RLHF对齐偏好**：人类标注者喜欢全面、安全、中立、礼貌、结构化，模型就学会列点、平衡、免责、总结。  
3. **解码策略**：低温度、贪心搜索让模型选高频词，如“首先”“其次”“总之”，人类会选意外、具体、低概率词。  
4. **翻译腔影响**：英文语料导致“基于……”“对于……而言”“进行……处理”等表达。  
5. **缺乏具身经验**：模型没有身体、生活、情绪，只能抽象概括，写不出“昨天我在菜市场……”这种细节。  
6. **长文规划需要模板**：为了连贯，模型倾向总分总、三点式、每段回扣。  
7. **产品化需求**：聊天机器人要显得专业、清晰、无害，所以爱用Markdown、列表、免责声明。  
8. **中文公共语体本身套话多**：AI只是把这种“平均文体”放大了。

## 二、结构特点

按“词→短语→句→句群→段→篇→标点→排版”从小到大看。

### 1. 用词特征

**高频抽象名词/黑话**：赋能、抓手、闭环、生态、维度、颗粒度、底层逻辑、范式、路径、对齐、落地、复盘、协同、增效、深耕、布局。  
例子：  
- 人话：“帮公司多赚钱。”  
  AI味：“以技术赋能业务，打造增长闭环，提升运营颗粒度。”  
- 人话：“大家一起干。”  
  AI味：“强化协同，推动落地，实现生态共建。”  
- 人话：“想清楚再干。”  
  AI味：“对齐底层逻辑，明确核心路径。”

**高频短语/缓冲语**：在一定程度上、从某种意义上说、总体而言、相对而言、值得注意的是、需要指出的是、不可否认、毋庸置疑、因人而异、需结合实际情况、不构成建议、请咨询专业人士。  
例子：  
- 人话：“你说得不对。”  
  AI味：“从某种程度上说，这一观点有一定合理性，但仍需进一步商榷。”  
- 人话：“别买。”  
  AI味：“是否购买需结合个人实际情况综合判断，必要时请咨询专业人士。”  
- 人话：“我不确定。”  
  AI味：“目前尚缺乏足够信息，需结合具体情境进一步评估。”

**连接套话**：首先、其次、再次、最后、此外、与此同时、然而、因此、总之、综上、由此可见、换言之、这意味着。  
例子：  
- 人话：“我饿了，去吃饭。”  
  AI味：“首先，当前已到用餐时间；其次，身体需要补充能量；因此，建议尽快就餐。”  
- 人话：“他不来，算了。”  
  AI味：“由于对方未能到场，因此本次活动需相应调整安排。”

**四字格与口号**：行稳致远、扬帆起航、保驾护航、提质增效、降本增效、共创未来、未来可期、久久为功。  
例子：  
- 人话：“好好干。”  
  AI味：“让我们携手共进，行稳致远，共创美好未来。”  
- 人话：“注意安全。”  
  AI味：“筑牢安全防线，为高质量发展保驾护航。”

**模糊限定/免责**：可能、或许、在一定程度上、建议结合自身情况、不构成投资建议、请咨询专业人士。  
例子：  
- 人话：“这股票会涨。”  
  AI味：“该标的未来走势存在不确定性，不构成投资建议，请理性判断。”  
- 人话：“我觉得不行。”  
  AI味：“该方案在部分场景下可能面临一定挑战。”

**术语化/翻译腔词**：基于、对于……而言、进行……处理、实现……提升、推动……发展、具备……能力、以……为核心。  
例子：  
- 人话：“我处理了这个问题。”  
  AI味：“该问题已得到有效处理。”  
- 人话：“做个给老人用的App。”  
  AI味：“打造一个以老年用户为中心、具备多模态交互能力的智能应用。”

### 2. 语句结构特征

**句式高度模板化**：不仅……而且……甚至……；既……又……；不是……而是……。  
例子：  
- 人话：“这工具好用。”  
  AI味：“它不仅提升了效率，也优化了体验，更重塑了工作方式。”  
- 人话：“这是挑战也是机会。”  
  AI味：“它既是挑战，也是机遇；既是压力，也是动力。”

**平衡句式：不站队，先说两面**：一方面……另一方面……；虽然……但是……；既要……也要……。  
例子：  
- 人话：“加班不好。”  
  AI味：“一方面，加班可能带来短期产出；另一方面，长期加班也可能影响健康，因此需理性平衡。”  
- 人话：“这电影一般。”  
  AI味：“该影片在视听层面有一定亮点，但在叙事层面仍存在提升空间。”

**动宾结构、名词化，把动作变公文**：通过……实现……；对……进行……；推动……落地；实现……提升。  
例子：  
- 人话：“我们改进了流程。”  
  AI味：“通过优化流程、整合资源、强化协同，实现了效率的显著提升。”  
- 人话：“我修好了电脑。”  
  AI味：“对设备故障进行了排查与修复。”

**被动、无主句**：已得到、被广泛认为、得到了有效落实、推动了发展。  
例子：  
- 人话：“他们解决了问题。”  
  AI味：“该问题已得到有效解决。”  
- 人话：“大家觉得很好。”  
  AI味：“该方案获得了较为广泛的认可。”

**长定语、嵌套、翻译腔**：基于……的、面向……的、具备……的、以……为核心的。  
例子：  
- 人话：“他迟到了，因为堵车。”  
  AI味：“他之所以迟到，是因为交通拥堵这一不可控因素所致。”  
- 人话：“给小孩用的书。”  
  AI味：“面向儿童认知发展阶段的启蒙阅读材料。”

**逻辑过度显化**：因此、由此可见、换言之、这意味着。  
例子：  
- 人话：“他没钱，没去。”  
  AI味：“由于资金受限，因此他未能成行。”  
- 人话：“天黑了，回家吧。”  
  AI味：“随着天色渐暗，因此建议尽快返程。”

**排比、递进、升华**：不仅……也……更……；既是……也是……更是……。  
例子：  
- 人话：“多读书有用。”  
  AI味：“阅读不仅增长知识，也拓宽视野，更塑造人格。”  
- 人话：“别放弃。”  
  AI味：“唯有坚持，才能穿越周期；唯有奋斗，才能抵达远方。”

**设问自答、定义式开头**：什么是……？简单说，……。所谓……，是指……。  
例子：  
- 人话：“AI味就是套话多。”  
  AI味：“什么是AI味？简而言之，它是一种高度模板化、结构化、安全化的表达倾向。”  
- 人话：“拖延就是不想干。”  
  AI味：“所谓拖延，通常指个体在任务推进过程中出现的非理性延迟行为。”

### 3. 段落结构特征

**总分总**：开头背景，中间分点，结尾升华。  
典型模板：  
“在当今数字化时代，随着……的发展，……越来越重要。首先……其次……最后……。综上所述，……具有重要现实意义。”  
例子：  
- 人话：“多喝水。”  
  AI味：“在健康管理日益受到重视的背景下，饮水作为基础环节具有重要意义。首先，……其次，……最后，……。总之，科学饮水有助于提升生活质量。”

**三点式、清单式**：第一、第二、第三；优势、挑战、建议；是什么、为什么、怎么办。  
例子：  
- 问“要不要考研？”  
  AI味：“一、评估目标；二、分析成本；三、制定计划；总之，理性选择。”  
- 问“怎么学编程？”  
  AI味：“首先，明确目标；其次，系统学习；再次，项目实践；最后，持续复盘。”

**每段主题句+解释+例子+回扣**：  
“在……方面，……。例如，……。因此，……。”  
这种段落非常整齐，但像报告。

**段落均匀、过渡词密集**：每段长度差不多，段首“与此同时”“除此之外”“值得注意的是”。

**不表态，最后“因人而异”**：  
例子：  
- 问“该不该买房？”  
  AI味：“买房有稳定性，也有流动性风险；租房有灵活性，也有不确定性；需结合自身情况综合判断。”  
- 问“该不该辞职？”  
  AI味：“辞职可能带来新机会，也可能带来风险；建议评估现状、分析风险、制定计划。”

**结尾升华/号召**：希望对你有所帮助、让我们一起、未来可期、只有……才能……。  
例子：  
“总之，只有不断学习，才能拥抱未来。让我们一起努力，共创美好明天！”

**缺少叙事弧线**：没有冲突、转折、情绪、失败、自嘲、个人经历。  
例子：  
- 问“创业难吗？”  
  AI味：“创业具有高风险高回报特征，需综合评估资源、能力与市场环境。”  
  人话：“我创业第一年赔了20万，合伙人跑了，猫还病了。”

### 4. 语义特征

**抽象概括，正确但空**：说的都对，但换任何场景都成立。  
例子：  
- AI味：“要提升认知，优化方法，持续行动。”  
  人话：“你先把手机锁抽屉里，干完活再刷。”

**缺少具体细节**：没有时间、地点、人名、数字、感官、动作、心理。  
例子：  
- 问“怎么减肥？”  
  AI味：“合理饮食，适量运动，保持作息，长期坚持。”  
  人话：“我三个月不吃夜宵，每天走一万步，瘦了八斤，但周末会破功。”

**缺乏具身经验**：没有身体感、生活感、情绪感。  
例子：  
- AI味：“失败是成长的一部分。”  
  人话：“那天我蹲在楼道里，外卖凉了，眼泪掉进汤里。”

**安全中立、免责**：不站队、不冒犯、不绝对。  
例子：  
- AI味：“这个问题没有标准答案，需辩证看待。”  
  人话：“我觉得就是不行。”

**全知视角、无个人立场**：像报告，不像“我”。  
例子：  
- AI味：“人们普遍认为……”  
  人话：“我以前也这么想，后来发现不是。”

**因果过度显化、同义反复**：  
例子：  
- AI味：“我们需要在战略上高度重视，在战术上精准施策，在执行上狠抓落实。”  
  人话：“赶紧干。”

**万能适配、可替换**：把主语换成任何项目都成立。  
例子：  
- AI味：“该方案通过资源整合与流程优化，实现了降本增效，为业务发展赋能。”  
  人话：“这方案砍了两个审批，省了三天，少花两万。”

**情绪中性、无冲突**：很少有愤怒、偏爱、后悔、自嘲、偏见。  
例子：  
- AI味：“该做法存在一定争议。”  
  人话：“这做法挺烦人的。”

### 5. 标点特征

**大量引号**：强调、术语、反讽。  
例子：  
“所谓‘底层逻辑’，其实是把简单事说复杂。”

**破折号**：解释、递进、转折。  
例子：  
“这不仅是一种方法——更是一种思维方式。”

**冒号**：引出列表、定义、结论。  
例子：  
“核心有三点：第一，……；第二，……；第三，……。”

**分号**：并列、对称。  
例子：  
“它既是机会；也是挑战；更是责任。”

**括号**：补充英文、解释、限定。  
例子：  
“人工智能（Artificial Intelligence, AI）正在……”

**省略号**：留白、委婉、抒情。  
例子：  
“或许，这就是成长吧……”

**感叹号**：号召、升华。  
例子：  
“让我们一起努力吧！”

**问号**：设问自答。  
例子：  
“什么是AI味？简单说，就是套话太多。”

**顿号**：并列堆叠。  
例子：  
“赋能、闭环、抓手、生态、维度、颗粒度。”

### 6. 排版特征

**Markdown重度使用**：标题、加粗、列表、表格、分隔线、引用块。  
典型：  
```
## 一、核心观点
**AI味**主要体现在：
1. **用词**：高频套话
2. **句式**：排比长句
3. **结构**：总分总
> 总之，……
---
希望以上内容对你有帮助！
```

**小标题层级过多**：一、二、三；（一）（二）；1. 2. 3.；-；✅。

**加粗关键词**：**注意**、**核心**、**关键**、**重点**。

**表格对比**：  
| 维度 | 特征 | 例子 |
|---|---|---|
| 用词 | 套话 | 值得注意的是 |
| 句式 | 排比 | 不仅……而且…… |

**emoji、符号、中英混排**：🌟、📌、✅、🚀；AI、Prompt、Token。

**结尾礼貌**：“希望以上内容对您有所帮助，欢迎继续交流。”

# 编程提示词

## 规划提示词1
> 摘自：Jorge RebollolIA

不要告诉它想要什么
告诉它：
想要实现什么
有哪些可用信息
存在哪些限制
优先考虑什么
想要避免什么
以何种方式收到回答
它需要猜测得越少，结果就越好。

1. “给我做一个计划” 改为 “我想在[期限]内实现[目标]。我有这些资源:[资源]，还有这些限制:[限制]。请创建一个分阶段的计划，按优先级排序，并告诉我应该先做什么。”

你不需要更多步骤。
你需要更好的标准。

2. “给我一些想法” 改为 “给我10个针对[类型的人群]、以实现[目标]的想法。避免那些到处都有的老生常谈的建议。按影响力和执行难易程度排序，并简要解释为什么你会选择前两个最佳建议。”

3. “分析这个” 改为 “从5个角度分析这个:优势、劣势、可能被我忽略的风险、机会以及可能的改进。然后给我一个结论，并告诉我如果目标是[目标]，你会先改变什么。”

分析并不意味着描述。
它意味着找到你没有看到的东西。

4. “帮我解决这个问题” 改为 “首先识别问题的真正原因。然后给我3个可能的解决方案，包括各自的优点、缺点和执行难度。推荐一个，并将其转化为我今天就可以开始实施的具体步骤。”
不要要求快速回答。
让它在回应你之前先思考。

## Agent.md设置

> 摘自：daisy https://mp.weixin.qq.com/s/lyjKtDPyOLavVJZBHmOcVw

本文件中的每一条规则都是强制性的。违反任何一条规则都会遭受毁灭性打击。

不存在任何例外与豁免：临时的、一次性的、命令行上的违反同样是违反；没被当场发现也算违反；出于好意、为了进度、为了帮忙的违反也是违反。

语言不允许使用"不是...而是..."句式；如果不需要对比的话，就不要对比；不要在任何话说完之后都提一句"不是其他的xxx"。如果没有叫你进行对比，就不允许使用"不是...而是..."、"要...而不是..."等类似的句式，你根本就没有需要说"不是"的对象，不要虚空打靶。

所有类似的句式都不允许使用。

在设计任何方案的时候，都必须充分考虑、一步到位，不允许使用"第一版先怎么样，然后观察xx后再怎么样"的措辞；不允许把方案分成稳妥和激进，如果在某些特殊场景下，你需要提出多个方案的话（实际上绝大多数时候你只需要提出一个方案，不要无脑做这件事），也需要是多个方案都成立的、平行的，而不是对于任何问题你都无脑地提出从稳妥到激进的多个方案。

## 4. 自动化测试体系（对应约定 4）

自动化测试是总称，由若干层组成，客户端交互自动化是其中一层。所有层共用统一的执行入口、产物规范与失败判定。

### 4.1 分层定义

| 层级 | 名称 | 覆盖对象 | 执行入口 | 进入 `verify` | 耗时预算 | 主要产物 |
|---|---|---|---|---|---|---|
| L1 | 单元测试 | 纯逻辑、状态机、校验函数、边界条件 | `./scripts/test-unit` | 是 | 秒级 | 控制台摘要 + JUnit XML |
| L2 | 集成测试 | 模块间协作、存储读写、序列化往返 | `./scripts/test-integration` | 是 | < 60s | JUnit XML |
| L3 | 端到端冒烟 | 主流程接口链路、启动与退出 | `./scripts/test-e2e` | 是 | < 3min | JSON 报告 + 日志 |
| L4 | **客户端交互自动化** | 真实界面操作：点击、拖拽、按键、输入、快捷键 | `./scripts/test-ui` | 是（冒烟子集） | 单例 < 30s，子集 < 5min | `report.json` + 步骤截图 + HTML 报告 |
| L5 | 自检 | 运行环境、依赖版本、配置项、数据目录可写 | `./scripts/selfcheck` | 是 | 秒级 | 检查表 |
| L6 | 视觉回归（可选） | 关键页面截图与基线比对 | `./scripts/test-visual` | 否，夜间执行 | < 10min | 差异图 + 差异像素占比 |

用例归属原则：能在 L1 用纯函数验证的逻辑，不写进 L4。L4 只覆盖真实交互路径与界面状态变化。

### 4.2 统一入口

```
./scripts/verify            # 串起 L1 → L2 → L3 → L5，默认包含 L4 冒烟子集
./scripts/verify --full     # 追加 L4 全量
./scripts/verify --layer ui # 只跑指定层，Agent 调试用
```

`verify` 输出汇总表，列出每层用例数、通过数、失败数、耗时、产物目录，按失败总数返回退出码。任一层失败，后续层是否继续由 `--fail-fast` 控制，默认继续以便一次看到全部问题。

### 4.3 产物规范（所有层共用）

| 产物 | 位置 | 内容 |
|---|---|---|
| 汇总表 | `.cache/test-reports/summary.json` | 每层统计与退出码 |
| 机器可读报告 | `.cache/test-reports/<layer>/report.json` | 每用例状态、耗时、失败原因、产物引用 |
| 人类可读报告 | `.cache/test-reports/<layer>/report.html` | 时间线、缩略图、失败堆栈 |
| 截图 | `.cache/test-reports/<layer>/screenshots/<用例ID>/` | 仅 L4、L6 产生 |
| 日志 | `.cache/test-reports/<layer>/logs/` | 运行日志与错误输出 |

`.cache/` 整体不入库，删除即彻底清理。

### 4.4 失败处理与回归保护

- 修 bug 时先补一个能复现的失败用例，再改代码到用例变绿；
- 用例失败时保留现场产物，禁止删除失败截图或报告；
- 偶发失败允许重试 ≤2 次，重试必须记入报告；同一用例连续多轮依赖重试通过，按缺陷处理；
- 放宽断言、跳过用例、删除用例必须在 `docs/开发记录.md` 写明理由与后续处理计划；
- 新增业务逻辑时，同一次提交内附上对应层级的测试；只改文档或脚本时 L1–L3 仍要跑。

## 5. 客户端交互自动化（自动化测试 L4 子模块，对应约定 5）

本节是 §4 体系下的一层，规则服从 §4 的统一入口与产物规范，以下为客户端特有的要求。

### 5.1 能力要求

| 能力 | 要求 |
|---|---|
| 元素定位 | 优先语义定位（角色 + 名称、测试 ID），禁止依赖像素坐标与 DOM 层级 |
| 交互原语 | `click` / `doubleClick` / `rightClick` / `drag(from,to)` / `type` / `press(key)` / `hotkey` / `scroll` / `hover` |
| 等待 | 显式等待条件（元素可见、文本出现、网络空闲、状态码），全局禁用固定 `sleep` |
| 断言 | 元素存在与状态、文本内容、列表数量、视图切换、接口调用次数 |
| 截图 | 关键步骤截图、失败自动截图、可选视觉比对 |
| 结果输出 | `report.json`、`report.html`、截图目录，格式与 §4.3 一致 |

### 5.2 选型（按栈取一个，保持单一）

| 客户端形态 | 推荐方案 |
|---|---|
| Web / Electron | Playwright（内置拖拽、截图、Trace、视频） |
| Tauri / 原生桌面 |  mcp-tauri-automation |
| 移动端 | Appium 或框架官方 UI 测试 |
| 兜底（无自动化接口） | 系统级键鼠 + 屏幕截图工具，如dsh-computer-use，仅作最后手段，必须固定窗口尺寸、缩放比例、主题 |

优先使用框架原生自动化接口。兜底方案要求锁定窗口尺寸与 DPI，否则脚本不可重复。

### 5.3 目录结构

```
scripts/
  verify                  # 总入口，对应 §4.2
  test-ui                 # L4 入口：跑全部或冒烟子集
  ui/
    run-case              # 跑单个用例，Agent 调试用
    record                # 录制操作序列，生成用例骨架
    cases/
      001-login.click.yaml
      002-drag-reorder.drag.yaml
      003-shortcut-save.key.yaml
```

### 5.4 用例格式（声明式）

```yaml
id: 002-drag-reorder
name: 列表拖拽排序并持久化
setup:
  reset_data: true
  window: {width: 1280, height: 800}
steps:
  - action: goto
    target: "app://tasks"
  - action: waitFor
    target: {role: listitem, name: "任务A"}
  - action: drag
    from: {role: listitem, name: "任务A"}
    to:   {role: listitem, name: "任务C"}
    screenshot: before-after
  - action: press
    key: "Ctrl+S"
  - action: expect
    target: {role: listitem, index: 0}
    text: "任务A"
assert:
  - api_called: {path: "/tasks/reorder", times: 1}
  - screenshot_diff: {baseline: "002-final.png", tolerance: 0.02}
```

用例数据驱动、可重复、幂等。每个用例自带 `reset_data`，不依赖前一个用例的残留状态。

### 5.5 截图与结果反馈

截图作为执行证据，供 Agent 读图判断与人工复核。命名规范：`<用例ID>/<步骤序号>-<步骤名>.png`。失败时固定输出 `99-failure.png`，并额外保留失败前一步的画面，便于对比预期与实际。

截图策略：

| 模式 | 触发 | 说明 |
|---|---|---|
| 默认 | `./scripts/test-ui` | 关键步骤 + 失败点 + 用例结束 |
| 全量 | `--screenshot=all` | 每步一张，调试用 |
| 视觉回归 | `--visual-regression` | 输出 `diff.png` 与差异像素占比，对应 L6 |

`report.json` 中每步字段：`{step, action, status, duration, error, screenshot}`，Agent 可按步骤定位失败点。

### 5.6 Agent 调用方式

```
1. 运行 ./scripts/ui/run-case 002-drag-reorder --json
2. 读取 report.json；status=failed 时读 error 与 99-failure.png
3. 结合截图与失败步骤定位问题，改代码或用例
4. 重跑单例，再跑 ./scripts/test-ui 冒烟子集
5. 全绿后把用例数、截图路径、耗时写进 docs/开发记录.md
```

Agent 行为边界：

- 允许修改 `cases/` 下的用例与业务代码；
- 不得为让测试变绿而放宽断言或跳过用例，跳过需在记录中写明理由；
- 不得手动修图或删除失败截图；
- 新增交互路径时同时新增用例，与 §4.4 同一条提交。

### 5.7 稳定性要求

| 问题 | 对策 |
|---|---|
| 用例偶发失败 | 显式等待 + 重试 ≤2 次，重试计入报告，频繁重试视为缺陷 |
| 数据互相污染 | 每例独立数据目录 + 独立临时端口 + 启动即重置 |
| 环境差异 | 固定窗口尺寸、DPI、主题、语言，时区与本地化写死 |
| 并行 | 默认并行，共享资源的用例标注 `serial: true` |
| 时长 | 单例 < 30s，冒烟子集 < 5min，超时即失败并截图 |

## 其他约定

- **所有构建缓存都在工作区 `.cache/` 内**：包管理器缓存、构建缓存、工具缓存、测试产物，删除该目录即可彻底清理，不影响用户目录。
- 服务端数据文件与客户端本地缓存库路径以项目实际为准，均支持用环境变量覆盖。
- 服务端默认只监听回环地址；令牌密钥等敏感配置请通过环境变量覆盖后再对外提供服务。
- 若工作区位于特殊文件系统（如移动硬盘、网络盘），构建脚本应提供**依赖预解包/复制**的兼容路径，详见[开发与构建](docs/开发与构建.md)。
